2. なぜ分けてるか・何をやらせてるか・どう回してるか

なぜロールを分けてるのか

最初は1ロール（PM）で全部やってた。でも問題が出た：

  • データ分析とマーケ施策の知識が混ざる — 分析の学びとマーケの学びが同じmemory.mdに入って、どっちの文脈かわからなくなる
  • 判断と作業が混ざる — 「この施策やるべき？」の判断と「じゃあ具体的にどう設計する？」の作業を同じロールがやると、判断が雑になる
  • 専門性が育たない — 何でも屋は何にも詳しくならない

分けた結果：各ロールの記憶が専門分野に集中して、精度が上がった。

各ロールが実際にやってる業務

CEO 判断・振り分け

自分では手を動かさない。「何を」「誰に」「なぜ」やらせるかを決めるだけ。

実際の業務：

  • 朝の状況把握 → tasks.json見て今日やるべきことを判断
  • CIOにデータ取得を指示（「BMI診断の効果データ出せ」）
  • CIOの分析結果を受けて、CMOに施策を振る（「MCV率が低い。改善案出して」）
  • CMOのアウトプットを品質チェック（検索意図と合ってるか？データの裏付けあるか？）
  • renに報告（結論 + 推奨アクション + GOでいい？）

やっちゃダメなこと：コード書く、データ集計する、マーケの中身を語る。全部専門家に振る。

CIO データ分析

数字を出して「何が起きてるか」「なぜか」を明らかにする。

実際の業務：

  • GOAL進捗スキャン（友だち数・売上の達成率、残り日数からペース計算）
  • 異常検知（3日連続で下がってるKPIを自動検出）
  • 施策の効果判定（PU設置後3-5日のデータで効果あり/なし判定）
  • ジャンル別・記事別の深堀り分析（CEOに「なぜ落ちてるか」を報告）
  • CMOにデータを渡す（施策設計の根拠として）

CMO マーケティング施策

「ユーザーの頭の中」から施策を設計する。

実際の業務：

  • LINE診断の設計（設問・結果タイプ・LP導線）
  • PU（ポップアップ）の訴求文言設計
  • 記事トリアージ（どの記事を優先的に改善するか、理由つきで）
  • デザイナー向けブリーフ（設計書）を自動生成
  • CIOのデータを受けて「だからこう改善すべき」を提案

CTO システム・開発

コードを書く唯一のロール。

実際の業務：

  • ダッシュボード（line-dashboard）の開発・修正
  • データパイプラインの管理（CSVダウンロード→集計→可視化）
  • スキルファイルの修正・新規作成
  • システム障害対応（「数字がおかしい」→ バグ特定→修正）

どうコミュニケーション取ってるか

renは基本的にCEOとしか話さない。CIO・CMO・CTOには直接指示しない。

コミュニケーションの流れ
ren「おはよう」「GO」「違う」だけ
↕ 話す相手はCEOだけ
CEO判断して、適切なロールに振る
↓ 指示
CIOデータ出す
CMO施策作る

具体的な振り方 — renの一言からどう動くか

一番聞かれるのがここ。renの雑な一言を、CEOがどう分解して、誰にどんな指示を出すか。

原則：renは「何がしたいか」だけ言う。「誰にやらせるか」「どんなデータが必要か」はCEOが判断する。

パターン1：状況確認系

ren：「今月の調子は？」

CEOの頭の中：「renが知りたいのはGOALに間に合うペースかどうか。数字が要る」

  • → CIO 「GOAL vs 現状のGAP出せ。友だち数・売上・CVR、ジャンル別で。ペース計算もつけて」
  • → CIOのデータをCEOが受け取る
  • → CEOが「GOAL到達圏内 / 危ない」の結論を出してrenに報告

ポイント：CIOにはデータだけ出させる。結論はCEOが出す。

パターン2：改善系（CIO→CMOの直列）

ren：「この記事どうにかしたい」

CEOの頭の中：「まず何がボトルネックか特定して、それから改善案」

  • → CIO 「この記事のファネルデータ出せ。PV→PU→友だち→診断→MCV、どこで落ちてるか」
  • → CIO結果：「MCV率が他ジャンルの半分。診断後にLPに飛ばない」
  • → CMO 「CIOのデータ渡すから、MCV率改善の施策出して。ブリーフも作って」
  • → CEOがCMOの施策を品質チェック → renに報告

ポイント：CIOが先、CMOが後。データなしで施策を作らせない。

パターン3：効果検証系（CIOだけ）

ren：「PU設置した後の効果は？」

CEOの頭の中：「設置前後の比較データがあれば判定できる。CMOは不要」

  • → CIO 「〇〇PUの設置前5日間 vs 設置後5日間のデータ比較。友だち転換率・CTR・表示回数」
  • → CIO結果：「転換率 1.2%→2.6%（+117%）。効果あり」
  • → CEOが判定：効果ありなら継続、なしなら差し替え検討 → renに報告

ポイント：効果判定はデータだけで完結するからCIOだけ。CMOに振る必要がない。

パターン4：新規作成系（CIO+CMO並列）

ren：「新しい診断作りたい。美容整形」

CEOの頭の中：「検索意図の分析と施策設計を同時に走らせたい」

  • → CIO 「美容整形ジャンルの流入KW上位10個を意図分類して。ボリュームも」（並列）
  • → CMO 「美容整形の診断設計ブリーフ準備して。CIOのKWデータ来たら反映して」（並列）
  • → 両方の結果が揃ったら、CEOが部門間MTGを設定（CIOデータ × CMO設計を突き合わせ）
  • → 合意した内容をrenに報告

ポイント：独立した作業は並列で動かす。待ち時間を減らす。

パターン5：障害系（CTOだけ）

ren：「ダッシュボードの数字おかしい」

CEOの頭の中：「システム障害。CEOが触ったら壊す。CTOの仕事」

  • → CTO 「ダッシュボードの〇〇の数字が合ってない。原因特定して直せ」
  • → CTO：「data_loader.pyのnormalize処理が原因。修正完了」
  • → CEOが確認 → renに「直った」と報告

ポイント：CEOは絶対にコードを触らない。触ると壊す（実際に壊したことがある）。

まとめ：振り方の判断基準

・データが必要 → CIO
・施策/設計が必要 → CMO（ただしCIOのデータが先）
・コード/システムの問題 → CTO
・データだけで完結する判断 → CIOだけ。CMO不要
・独立した作業 → 並列で動かす
・データが施策の前提 → 直列（CIO先→CMO後）

品質をどう上げてるか

2つの仕組みで品質を担保してる。

① CEOの品質ゲート

CIO・CMOのアウトプットをrenに出す前に、CEOがチェックする。

  • 計算の根拠はあるか？（CIOの数字が正しいか）
  • ユーザーの頭の中から始まってるか？（CMOの施策が的外れじゃないか）
  • GOALへの貢献度は示されてるか？
  • 「どうする？」で終わってないか？（判断投げになってないか）

→ NGならrenに出さずにCIO・CMOに差し戻す。renが見るのは品質チェック済みのものだけ。

② CIOとCMOの壁打ち（部門間MTG）

CIOのデータとCMOの施策を突き合わせて、お互いに検証する。

  • CIO：「この施策、データ的に根拠ある？他に見るべき数字は？」
  • CMO：「この数字の裏に、ユーザー体験の問題があるんじゃない？」
  • 2-3ラウンドで合意 → 合意した内容をCEOに上げる

結果：renが「違う」と言う回数が減る。

品質ゲート + 部門間MTGで、renに上がる前にほとんどの問題が潰される。
renの仕事は「GO」を出すことに集中できる。
